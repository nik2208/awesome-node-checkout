## [2.2.0] - Unreleased

### Added
- **Charge lookup** (read-only): `CheckoutConfigurator.getCharge(provider, chargeRef, options?)` answers "did money move for this `chargeRef`?" for an `unknown` charge that may not be retried, telling an authenticated "no transaction" (`absent`) apart from a lookup that failed (`unknown`). It never charges, never refunds, emits no event and is not a route. It validates first without calling the provider (`INVALID_MANDATE_REQUEST`: `chargeRef` against `CHARGE_REF_PATTERN`, `options.since` / `options.until` with a finite `Date.parse` and `until >= since`, `options.mandate` of this provider) and normalizes fail closed into a new object (only an exactly `verified: true` answer is `succeeded`, `failed`, `pending` or `absent`; an `unknown` one is never verified and carries no payment facts; `chargeRef` is the request's; a provider that throws gives `unknown` with `raw` reduced to `{ name, message }`). Resolves #40.
- **`CheckoutConfigurator.supportsChargeLookup(provider)`** (`PROVIDER_NOT_FOUND` for an unregistered provider, like `supportsMandates`). Resolves #40.
- **Types** `ChargeLookupStatus` (`succeeded`, `failed`, `pending`, `absent`, `unknown`), `ChargeLookupOptions`, `ChargeLookupResult` and `ChargeProviderState` (`refunded`, `partially_refunded`, `partially_captured`), and the optional provider capability **`IChargeLookupProvider`** with **`isChargeLookupProvider`**, all exported. `IPaymentProvider` and `IMandateProvider` are unchanged, so existing custom providers keep compiling. Resolves #40.
- **`CheckoutErrorCode` `CHARGE_LOOKUP_NOT_SUPPORTED`**, thrown by `getCharge` for a provider without the capability (Satispay in 2.2.0) and mapped to HTTP 422 by the Express adapter's error handler. Resolves #40.
- **Nexi `getCharge`**: `situazioneOrdine` (bounded by `timeoutMs`), classified over every report entry like the replay guard: money taken → `succeeded` with the amount, currency, `providerStatus` (trimmed `stato`) and `providerState` of the most specific paid entry (the first refunded or partly captured one, otherwise the first paid one); all refused → `failed`; not final → `pending`; OK with no entry or a MAC-signed KO "not found" (2, 13) → `absent`; an unsigned KO "not found", and any HTTP, network, timeout, parse or MAC failure → `unknown`, without the response body in `error`. Resolves #40.
- **PayPal `getCharge`** by `invoice_id`: the Transaction Search API (`options.since` required, window `since − 1 h` .. `min(now, until + 1 h)`, at most 31 days, pages of 500, at most 10 pages; `total_pages: 0` on an empty first page is an empty window) locates the capture, and the authenticated `getCapturedPayment` re-read answers (`COMPLETED`, `PARTIALLY_REFUNDED`, `REFUNDED` → `succeeded` with the state; `PENDING` and any unknown status → `pending`; `DECLINED`, `FAILED` → `failed`; `providerPaymentId` = the order id). No match is `absent`, and a `DECLINED` / `FAILED` capture `failed`, only 4 hours after `until` (PayPal's 3-hour indexing delay: a later attempt may not be listed yet), and both are `unknown` before; the double-charge check sees only the captures already listed, so it is reliable only after that horizon. More than one distinct capture (a possible double charge), more than 5 matching records, or a capture of another `invoice_id` / `custom_id` are `unknown`. `raw` is the captured payment or PayPal's error body, never a search page or the SDK error. The `TransactionSearchController` is built on the first lookup. Requires "Transaction search" on the REST app. Resolves #40.
- **`refundedAmount`** (major units; `0` = the provider reports no refund, absent = it does not report it) on `ChargeLookupResult` (only on a verified `succeeded`: the configurator drops it otherwise, and when it is not a finite number ≥ 0) and on `PaymentResult` (set by PayPal `getPaymentDetails` only). PayPal sums the order's `COMPLETED` refunds in minor units (`PENDING` ones are not counted; another currency, an invalid value or more than one capture leaves it out, and so does a `REFUNDED` / `PARTIALLY_REFUNDED` capture whose order lists no `COMPLETED` refund, never `0`); `getCharge` reads the order only for a `REFUNDED` / `PARTIALLY_REFUNDED` capture whose order's first capture it is (`COMPLETED` is `0` with no extra call). Nexi reports `0` for a paid state without a refund and nothing for `Rimborsato` / `Rimborsato Parz.` (no documented source). Resolves #41.
- **`ChargeResult.providerState` and `providerStatus`**: a Nexi replay (replay guard or KO-9 re-read) of a charge now refunded (`Rimborsato`, `Rimborsato Parz.`) or partly captured (`Contabilizzato Parz.`) reports the state and the trimmed `stato`, so apps no longer parse `raw.stato` (kept byte-identical). With several report entries that took the money, `amount`, `currency`, `raw.stato` and `providerStatus` stay the first paid entry's, exactly as in 2.1.0 (so the configurator's amount check, and the replay's `status`, are unchanged), and `providerState` is set when any of them is refunded or partly captured: the two fields can then come from different entries. The configurator drops both from unverified results (including an unverified setup outcome's first charge), keeps them when the amount check turns the result `unknown`, and never changes `status` because of them (a refunded replay stays `succeeded`). `charge.*` events carry `data.providerState`. Resolves #42.
- **`ChargeResult.errorCode` and the type `ChargeErrorCode`** (exported): a stable, machine-readable reason set by the library on a charge result, so integrations stop matching the free-text `error`. The first code is `'AMOUNT_MISMATCH'`: the provider reports money taken for another amount or currency than requested; `status` is `unknown`, `amount` / `currency` are the reported ones when the provider gave them, and the charge must not be retried (a retry, a Nexi replay included, gets the same answer): review it, and refund or keep the money. The configurator sets it with `'Charged amount does not match the request'` (`chargeMandate` and every first charge), PayPal with `'Captured amount does not match'` (setup capture); both strings and every `status` stay byte-identical. A final `succeeded` never carries an `errorCode` (the configurator deletes one a provider set), nor does an unverified "success" turned `unknown`; on other statuses a provider's code is kept only when it is a known `ChargeErrorCode`; an unverified setup outcome's first charge carries none. `charge.*` events carry `data.errorCode`. More codes may be added in minor releases: treat an unknown code like no code. Resolves #43.
- **Refund idempotency keys**: `CheckoutConfigurator.refundPayment(provider, paymentId, amount?, options?)` with `RefundOptions.idempotencyKey` (one key per intended refund, stable across its retries, never reused; `REFUND_IDEMPOTENCY_KEY_PATTERN` `/^[A-Za-z0-9_-]{8,64}$/`), sent as PayPal `PayPal-Request-Id` (kept 45 days) and Satispay `Idempotency-Key` (retention not documented). A retry with the same key gets the provider's original answer instead of a second refund. The configurator validates before calling the provider or emitting `payment.refunded` (fail closed): options that are not an object, or a key that is not a string matching the pattern, throw `INVALID_REFUND_REQUEST`; a key on a provider without support (Nexi, a provider written for 2.1) throws `REFUND_IDEMPOTENCY_NOT_SUPPORTED`. Without options the provider is called with `(paymentId, amount)`, exactly as in 2.1; with them, with `(paymentId, amount, { idempotencyKey })`. A provider whose `supportsRefundIdempotency` is not `true` is always called with `(paymentId, amount)`: options without a key are not passed on to it. The Express route `POST /:provider/refund` is unchanged (body `{ paymentId, amount }`, no key). Called directly, `NexiProvider.refundPayment` with a key returns `{ success: false, status: 'REFUND_FAILED' }` without any request, and PayPal and Satispay do the same for a key that does not match the pattern. Resolves #44.
- **Types** `RefundOptions` and `REFUND_IDEMPOTENCY_KEY_PATTERN` (exported), the optional third parameter `options?: RefundOptions` of `IPaymentProvider.refundPayment` and `BasePaymentProvider.refundPayment`, and the optional capability flag **`IPaymentProvider.supportsRefundIdempotency`** (`true` on `PayPalProvider` and `SatispayProvider`, unset on `NexiProvider`). A provider written for 2.1, with the two-parameter `refundPayment` and no flag, keeps compiling and behaving the same (a compile-time check of that signature is part of `npm run typecheck`). **Caveat:** a 2.1 provider whose `refundPayment` already declared a third parameter of another type (for example `reason?: 'duplicate' | 'fraudulent'`) no longer compiles (TS2416 for a `BasePaymentProvider` subclass or a class implementing `IPaymentProvider`, TS2322 for an object typed `IPaymentProvider`); widening that parameter to accept `RefundOptions` too (`reason?: 'duplicate' | 'fraudulent' | RefundOptions`) makes it compile again without changing its callers (also a compile-time check), and at runtime the configurator never passes it anything, since it has no flag. Resolves #44.
- **`CheckoutErrorCode` `INVALID_REFUND_REQUEST`** (HTTP 400 through the Express adapter's error handler) **and `REFUND_IDEMPOTENCY_NOT_SUPPORTED`** (HTTP 422). Resolves #44.
- **`PayPalProviderConfig.timeoutMs`** (opt-in): passed to the SDK `Client` as `timeout`, it bounds every PayPal API call of the provider, the OAuth token request and the `getCharge` Transaction Search included. A call that exceeds it fails like a network error, through the existing error paths: `chargeMandate` and `getCharge` `unknown`, `confirmMandate` unverified and non-terminal with an `unknown` first charge, `getMandate` `unknown`, `revokeMandate` `revokedAtProvider: false`, and `createMandate`, `createPayment`, `executePayment`, `getPaymentDetails`, `refundPayment` `success: false` without `verified`; no part of the thrown SDK error (its config and request carry the bearer token) reaches a result or an event. Only a finite number > 0 is used: without it, or with `0`, a negative number, `NaN`, `Infinity` or a string, the `Client` gets no `timeout` key and nothing changes (no timeout, as in 2.1.0). It is the SDK's (axios) inactivity timeout, not a wall-clock deadline. 30000 is the recommended value; a future 3.0.0 can make it the default. Resolves #45.
- **Payment-method hints out of the persisted `Mandate`**: `confirmMandate` returns a setup's unsigned hints (Nexi masked PAN and card expiry, PayPal payer email) in the new **`MandateSetupOutcome.hints`**, of the new exported type **`MandateHints`** (`cardExpiry`, `maskedPan`, `payerEmail`), only on a verified outcome with `success: true` and only when there is at least one; every other outcome (unverified, mismatched, verified with `success: false`) has `hints: undefined`. The source is the provider's `outcome.hints` when it is an object, otherwise its `mandate.unverified`, never a merge; only the three keys with non-empty string values are kept, verbatim, in new objects (the provider's objects are never mutated). The new option **`CheckoutConfig.mandateHints`** says where else they go: `'inline'` (the default, and what any other value does) also keeps them in `outcome.mandate.unverified`, the 2.1 placement; `'separate'` returns a mandate with no `unverified` key, which can be persisted verbatim without the hints and charges, reads and revokes exactly the same. Every other mandate field is kept, so a field that a later minor adds is never lost. Providers and events are unchanged. Resolves #46.

### Changed
- **PayPal setup capture for another amount**: the first charge of a `COMPLETED` capture whose money differs from `pending` keeps `status: 'unknown'`, `verified: true`, `chargeRef` and `error: 'Captured amount does not match'`, and gains `errorCode: 'AMOUNT_MISMATCH'`, `providerPaymentId` (the PayPal order id: the money was captured, so `refundPayment('paypal', orderId, amount)` refunds it), and the captured `amount` and `currency` when PayPal reported them (a `COMPLETED` capture without a valid amount is the same mismatch, with neither). The outcome is still a terminal success with the vaulted mandate. Since the order id is now the first charge's `providerPaymentId`, it is no longer scrubbed from that setup's events (`mandate.created` and the first charge's `charge.unknown`), as for a successful capture: it is the refundable id, not a credential. Resolves #43.
- **A Satispay full refund first reads the payment** (`GET /payments/{id}`), because the documented refund requires `amount_unit`: unless the read answers this id, `ACCEPTED` and an integer `amount_unit > 0`, the result is `{ success: false, status: 'REFUND_FAILED', error: 'Satispay payment could not be read: no refund was sent' }` and nothing is sent. After an earlier partial refund, a full refund of the original amount is refused (4xx): pass the remaining amount explicitly. Resolves #44.
- **`outcome.mandate.unverified` is sanitized by `confirmMandate`** in the default mode: an empty `unverified` object is no longer returned, for example PayPal without an email (2.1 returned `unverified: { payerEmail: undefined }`, `{}` once serialized), so such a mandate has no `unverified` key. Keys other than `cardExpiry`, `maskedPan` and `payerEmail`, and values that are not non-empty strings, are now dropped from it (only a custom provider could have set them); every non-empty value from the built-in providers stays as in 2.1. It is now a copy of `outcome.hints`, no longer the provider's own object. Resolves #46.

### Deprecated
- **`Mandate.unverified`**: read `MandateSetupOutcome.hints`. It is still filled by default and never set with `mandateHints: 'separate'`; its type is now the named `MandateHints`, identical in shape to 2.1's. To be removed from `Mandate` in 3.0.0, where `'separate'` becomes the only behaviour. Resolves #46.

### Fixed
- **Nexi `getPaymentDetails` reads every report entry for the code**, selecting the entry as the replay guard of `chargeMandate` does since 2.1.0 (the first paid entry, else the first entry not final, else the first refusal) instead of the first matching one. A code listed `Negato` then `Contabilizzato` (a retry after a KO) is now `success: true`, `status: 'Contabilizzato'` (in 2.1.0: `success: false`, `'Negato'`). A report whose first entry is paid keeps its 2.1.0 result, so no `success: true` becomes `false`: a code listed `Autorizzato` then `Rimborsato` stays `success: true`, `status: 'Autorizzato'` (`getCharge` reports its refund as `providerState`). A report with no paid entry now reports the first entry not final, if any (`[Negato, In Corso]` is `status: 'In Corso'`, still `success: false`). `success` keeps its rule (a `NEXI_PAID_STATUSES` `stato` with a valid amount and currency); the transport, the KO branch, the MAC checks and `'Report not found'` are unchanged, and so is the replay guard's own selection. Resolves #40.
- **Satispay refunds use the documented flow and report a checked outcome.** A refund is now a new payment, `POST /g_business/v1/payments` with `flow: 'REFUND'`, `parent_payment_uid`, `amount_unit` and `currency: 'EUR'` (Satispay's API reference does not list the `POST /payments/{id}/refunds` called since 1.0.0). It is reported `success: true` (verified) only for a 2xx `ACCEPTED` refund with an id and a `type` absent or `REFUND_TO_BUSINESS` (in 2.1.0 any 2xx was a verified success, whatever its status). A refusal is told apart from an unknown outcome: any other 2xx, a network error or a timeout, and HTTP 401, 403, 408, 409, 429 and 5xx give `success: false` without `verified` (the refund may exist), while any other 4xx gives `{ success: false, verified: true, status: 'REFUND_FAILED', error: <Satispay's message> }` (nothing was refunded). Refunds still have no timeout unless `SatispayProviderConfig.timeoutMs` is set (it now bounds them when it is), and the invalid payment id and `INVALID_AMOUNT` results are unchanged. Check the three refund behaviours listed in the README on the Satispay sandbox before release. Resolves #44.
- **A failed PayPal OAuth token request no longer disables the `PayPalProvider`.** The PayPal SDK keeps the token request of a client and makes every later call of that client wait for it, so in 2.1.0 one failed token request (a reset connection, an HTTP error of `/v1/oauth2/token`, and with the new `timeoutMs` a token response slower than the timeout) made every later `chargeMandate`, `confirmMandate`, `refundPayment`, `getCharge` and other call of that instance fail at once with the same error, without being sent, until the app built a new provider. The provider now gives the SDK `Client` an `oAuthTokenProvider` that is the SDK default (`updateToken`) and, on a failure, replaces the SDK client before rethrowing: the calls waiting for that token fail exactly as in 2.1.0 (same error, same result), and the next call requests a new token. Without `timeoutMs`, a token request that never answers still stalls every later call of the provider. Resolves #45.

## [2.1.0] - 2026-11-12

Recurring payments (mandates): the core contract, configurator methods and Express routes. The built-in providers implement it in #31 (Nexi), #32 (PayPal) and #33 (Satispay). Resolves #30.

### Added
- **Mandate models** (`src/models/mandate.model.ts`, exported): `MandateSetupRequest`, `MandatePendingState`, `MandateSetupStart`, `Mandate`, `MandateStatus`, `ChargeRequest`, `ChargeResult`, `ChargeStatus`, `MandateSetupOutcome` (with `terminal`), `MandateCallbackInput`, `MandateStatusResult`, `MandateRevokeResult`, and the patterns `MANDATE_REF_PATTERN` (`/^[A-Za-z0-9_-]{5,30}$/`) and `CHARGE_REF_PATTERN` (`/^[A-Za-z0-9-]{2,30}$/`). All are plain JSON: the app persists them, the library keeps no mandate state in memory. Resolves #30.
- **`IMandateProvider`** (optional provider capability: `createMandate`, `confirmMandate`, `chargeMandate`, `getMandate`, `revokeMandate`) and **`isMandateProvider`**. `IPaymentProvider` is unchanged, so existing custom providers keep compiling. Resolves #30.
- **`CheckoutConfigurator`**: `supportsMandates`, `createMandate`, `confirmMandate`, `chargeMandate`, `getMandate`, `revokeMandate`. They validate inputs before calling the provider and normalize outcomes fail closed: an unverified outcome is never a success and never terminal; a verified outcome must match the pending setup (`firstCharge.chargeRef === pending.orderId`, `mandate.mandateRef`, `mandate.provider`); an unverified charge "success" and a verified one for another amount or currency become `unknown`, never `failed`; an unverified first charge carries no `providerPaymentId`, `amount` or `currency`; a revoked mandate is not charged; a provider that throws while charging gives `unknown`, whose `raw` (and the `charge.unknown` event's) is only the error's `{ name, message }`, never the thrown object, since SDK errors carry the request headers (bearer token) and body as own properties. `createMandate` returns `success: false` when the provider's `pending` does not match the request, `amount` and `currency` included (minor units, case-insensitive currency; a missing or invalid value never matches), because the first charge's amount check in `confirmMandate` trusts `pending`. `createMandate` requires absolute http(s) `returnUrl`, `cancelUrl` and (when set) `notifyUrl`, so a relative URL is a 400 `INVALID_MANDATE_REQUEST` instead of a provider-side `TypeError`. Resolves #30.
- **Events** `mandate.setup_started`, `mandate.created`, `mandate.setup_failed`, `mandate.revoked`, `charge.succeeded`, `charge.failed`, `charge.unknown`, `charge.requires_action`. Setup events are emitted only for terminal outcomes, so a forged callback never looks like a failed setup. Charge events carry `orderId = chargeRef` and `paymentId = providerPaymentId`; `data.mandateRef` is on every mandate event; the credential-like `providerMandateId` is never part of an event (scrubbed from the event's copy of `raw` and `error`, where binary values such as a `Buffer` become `'[binary]'` since they cannot be scrubbed; every setup event, `mandate.setup_started`, `mandate.created`, `mandate.setup_failed` and the first charge's `charge.*`, also scrubs `pending.providerRef`, the Satispay token id, from the whole payload, `raw`, `error` and `data` included, unless it is the `orderId`, the `mandateRef` or the first charge's `providerPaymentId`). Events can repeat for the same `orderId` (redirect plus notification, replays): listeners must be idempotent on it. **Listener errors on the events emitted after a provider call** (`mandate.created`, `mandate.setup_failed`, `mandate.revoked`, `charge.*`) never reject `confirmMandate`, `chargeMandate` or `revokeMandate`: the result is returned and the error goes to the new `CheckoutConfig.onListenerError(err, event)` hook, or to `console.error` without it. Every other event, `mandate.setup_started` included, still propagates `CheckoutListenerError`. Resolves #30.
- **`CheckoutErrorCode`** values `MANDATES_NOT_SUPPORTED` (HTTP 422 through the router) and `INVALID_MANDATE_REQUEST`. Resolves #30.
- **Express Adapter**: `mandates` option (`buildMandateRequest`, `onStarted`, `loadPending`, `onOutcome`, all required, else `INSECURE_CONFIGURATION` at mount; optional `middleware`) mounting `POST /:provider/mandate` and `GET|POST /:provider/mandate/callback`. The callback is always exempt from the shared `middleware`; `onStarted` runs before the response; the response never carries `pending` or `raw`; the pending state is single-use (documented contract of `loadPending` / `onOutcome`). `GET /:provider/mandate` answers 405 instead of reaching the details route. No route exists for charges or revocations. Exported type `ExpressMandateOptions`. Resolves #30.
- **`appendMandateRef(url, mandateRef)`** (exported): adds or replaces the `mandate_ref` query parameter, keeping the query and the hash. Resolves #30.
- **Nexi XPay mandates**: `NexiProvider` implements `IMandateProvider` (EUR only, since `pagamentoRicorrente` accepts only `978`). `createMandate` builds the hosted-page first payment that registers the contract (`num_contratto` = `mandateRef`, `tipo_servizio=paga_multi`, `tipo_richiesta=PP`, `codTrans` = `orderId`, `mandate_ref` appended to `url`, `url_back` and `urlpost`). `confirmMandate` verifies the 7-field outcome MAC and binds the outcome to the pending setup (MAC-covered `codTrans`, `importo`, `divisa`; the unsigned `num_contratto`, `tipo_servizio` and `tipo_richiesta` only as tampering indicators): a forged or mismatched outcome is unverified and non-terminal, OK is an active mandate with a `succeeded` first charge, `KO`, `ANNULLO` and `ERRORE` a terminal refusal, and any other `esito` (e.g. pending) unverified and non-terminal. Deviation from the issue's "if present" wording: an OK outcome without `num_contratto` is unverified and non-terminal, because the contract parameters of the `approvalUrl` are not MAC-covered and, without the echo, no contract may exist (Nexi's own `pagamento-ricorrente` samples read `num_contratto` from the outcome; to be confirmed against `int-ecommerce.nexi.it` before release). A MAC-verified `KO` is terminal, so the terminal must allow a single payment attempt per `codTrans` (XPay can be configured for up to 3, sending a KO and then an OK for the same `codTrans`); the `urlpost` notification must be answered with HTTP 200 (manual, pp. 22-23 and 33), because a terminal set to void on notification failure cancels the authorization otherwise. ## [2.0.0] - 2026-11-12

Every permissive default of `createCheckoutRouter` becomes an explicit, named opt-in. Resolves #29.

### Breaking
Migration list:
- **The router throws at mount without `buildPaymentRequest`.** `createCheckoutRouter(checkout)` now throws `CheckoutError` with the new code `INSECURE_CONFIGURATION`. Set `buildPaymentRequest` (server-side amount), or, only where the client may choose the amount, `allowClientPaymentRequest: true` (prints one `console.warn` at mount). The old mount warning `the client body decides the amount; set buildPaymentRequest` is gone.
- **The details route `GET /:provider/:id` is not mounted by default.** Add `details: { middleware: [...] }` to mount it behind your auth. `details: {}` mounts it unprotected and prints one `console.warn`. `details.enabled` is deprecated: `enabled: false` behaves as omitted (Express 404 instead of the former JSON `'Payment details route is disabled'`).
- **`amount` values with excess decimals now fail instead of being rounded.** Through the router, an amount with more decimals than the currency allows (`19.999` EUR, `10.5` JPY) answers `400 { success: false, code: 'INVALID_AMOUNT', error }` (new `CheckoutErrorCode`) without calling the provider; `0`, negative and non-finite amounts keep their earlier 400 (`INVALID_PAYMENT_REQUEST` from `buildPaymentRequest`, uncoded on the client-body path). Called directly, Nexi, Satispay and PayPal `createPayment` reject all of these (excess decimals, `0`, negative, non-finite) with `INVALID_AMOUNT` and return `{ success: false, status: 'FAILED', error }`, and so does `refundPayment` for a partial amount with excess decimals, `0` or a negative value (only an omitted `amount` refunds in full; Nexi and Satispay previously treated `0` and `null` as a full refund, and now reject them like PayPal). Amounts are checked against the ISO 4217 exponent of the currency (0, 2 or 3). PayPal formats payment and refund amounts with that exponent, so it now receives `'1000'` for 1000 JPY (previously the rejected `'1000.00'`) and `'1.200'` for 1.2 KWD. **Nexi and Satispay `createPayment` now reject currencies whose exponent is not 2** (JPY, KWD, …, and Nexi numeric codes such as `392`) with `{ success: false, status: 'FAILED', error }`: their outcome amounts and refunds are in hundredths, so only 2-decimal currencies keep the created, reported and refunded amounts on the same scale.
- **500 response bodies are generic.** Unexpected errors answer `{ success: false, error: 'Internal server error' }`. Set `exposeErrorMessages: true` to get the previous messages (including the `'Invalid provider response'` masking). The error is passed to the new `onError(err, req)` option, or logged with `console.error('[awesome-node-checkout]', err)` when `onError` is not set. `CheckoutError` 4xx responses keep their message and code.
- **Generated order ids changed format.** Without `orderId`, Nexi `codTrans` and Satispay `external_code` are `ORD-` + 24 random hex chars (28 chars) instead of `ORD-<Date.now()>`.

### Security
- **Express Adapter**: the client body can no longer decide the amount unless `allowClientPaymentRequest: true` is set explicitly; previously a missing `buildPaymentRequest` only logged a warning and `POST /checkout/paypal {"amount":0.01,…}` created a 0.01 payment. Resolves #29.
- **Express Adapter**: `GET /:provider/:id` is opt-in, so status, amount and currency of a payment are no longer readable by anyone who knows (or, for Nexi, guesses) a payment id. Resolves #29.
- **Nexi, Satispay**: generated order ids come from `crypto.randomBytes` (96 bits) instead of a millisecond timestamp: they cannot be enumerated and do not collide across instances or within the same millisecond. Resolves #29.
- **Nexi, Satispay, PayPal**: amounts are converted to exact minor units for the currency (`toMinorUnits`/`toMajorString`, internal); an excess decimal is rejected instead of silently rounded. PayPal no longer formats zero/three-decimal currencies with two decimals; Nexi and Satispay reject them at `createPayment`, so for payments created through this library the created, reported and refunded amounts are on the same scale (outcome amounts are still read in hundredths, whatever the `divisa`/`currency`). A refund `amount` of `0` or `null` no longer turns into a full refund on Nexi and Satispay. Resolves #29.
- **Express Adapter**: internal error messages (including those thrown by `buildPaymentRequest`, `onBeforeExecute`, `redirect` handlers and event listeners) no longer reach the client in 500 responses by default. Resolves #29.

### Added
- `ExpressCheckoutOptions.allowClientPaymentRequest`, `exposeErrorMessages` and `onError`. Resolves #29.
- `CheckoutErrorCode` values `INSECURE_CONFIGURATION` and `INVALID_AMOUNT`. Resolves #29.

### Unchanged
- `POST /:provider/execute` stays mounted by default: capturing an approved payment only completes the payer's own payment, and since 1.3.0 the outcome is keyed on the provider-authenticated id (#27). Documented in the README.

### Documentation
- README: "Secure defaults (2.0)" section, details marked *opt-in* in the Routes table, Quick Start and Express examples always build the request server-side. Resolves #29.

## [1.2.0] - 2026-09-27

### Security
- **Nexi**: Fail-closed outcome MAC verification on redirect and webhook. Missing or invalid `mac` parameter rejects payment with status `FAILED` and error `'MAC missing'`. Verifies 7-field formula (`codTrans`, `esito`, `importo`, `divisa`, `data`, `orario`, `codAut`, `macKey`) using constant-time comparison `crypto.timingSafeEqual`. Resolves #6.
- **Express Adapter**: `publicPaths` now uses segment-based path matching rather than substring matching, preventing subpath bypasses such as `/webhook/execute` or `/redirect/execute` when `/webhook` or `/redirect` is marked public. Resolves #13.

### Fixed
- **Nexi**: Updated `getPaymentDetails` to query the official BackOffice endpoint `POST /ecomm/api/bo/situazioneOrdine` with JSON payload and response MAC verification instead of the non-existent IGFS endpoint. Resolves #7.
- **Satispay**: Fixed webhook handling for GET callbacks containing `payment_id` query parameter, ensuring callbacks routed to `handleWebhook` correctly extract payment details and verify signatures. Added configurable `callbackPath` (defaulting to `/checkout/satispay/webhook`). Resolves #10.
- **Satispay**: Fixed HTTP signature verification to support `(request-target)` pseudo-header via request context, signature header without `(request-target)`, flexible header key order, and body digest verification. Resolves #11.

### Added
- **Nexi**: Added server-to-server outcome notification support (`urlpost`) configured via `PaymentRequest.notifyUrl` in `createPayment`, and handled via `NexiProvider.handleWebhook`. Resolves #8.
- **Core**: Exposed `amount` and `currency` in `PaymentResult` and `WebhookResult` across all providers (Nexi, PayPal, Satispay) to enable post-payment amount verification. Resolves #9.
- **Core**: Propagated `orderId` and `raw` provider response data through `CheckoutConfigurator` event bus payloads (`payment.created`, `payment.completed`, `payment.failed`, `payment.refunded`, `webhook.received`). Resolves #12.
- **Express Adapter**: Added `options.redirect` for automatic 302 HTTP redirects to `onSuccess(result, req)` or `onFailure(result, req)` on browser return. Resolves #12.
- **Express Adapter**: Added `options.details` configuration to gate or disable `GET /:provider/:id` (`enabled: false` returns 404, or custom `middleware`). Resolves #12.
- **Express Adapter**: Added context argument `{ provider, res }` to `buildPaymentRequest(req, ctx)` and strict validation of returned `PaymentRequest`. Resolves #12.
- **Express Adapter**: Mounted both `GET` and `POST` routes for `/:provider/webhook`. Resolves #10.
- **Packaging**: Added `"types"` condition to `exports` in `package.json` for TypeScript package resolution under `node16`/`nodenext`. Resolves #12.

### Changed
- **Nexi**: Breaking change in outcome verification: previously `handleRedirect` accepted outcomes without a `mac` field. It is now strictly required (fail-closed). Any integration testing Nexi callbacks must supply a valid `mac`.
